# ADR-0000: ADR ドキュメントフォーマットと設計ログ

## ステータス

accepted

## コンテキスト

重要な設計決定を「後から追跡・更新しやすい形」で残して追える必要がある
一方で、決定の背景や却下案が残らないと同じ議論が再発しやすい
ADR を肥大化させずに判断理由を補えるフォーマットが必要である

## 決定

### ADR の位置づけ

- 重要な設計決定は ADR として記録する
- 追加の議論メモは設計ログ ( Design log ) 側に分離し、ADR 本文は短く保つ

### ファイル名

- `docs/decisions/` 配下に置く
- `0000` のような 4 桁 0 埋め連番 + `-` + 英小文字の短いタイトル（kebab-case）

### ステータス語彙

- `proposed` / `accepted` / `rejected` の 3 種を使用する
- 本文中で `決定（提案）` のように混在させず、ステータスで状態を表現する

### 必須セクション

- ステータス（`proposed` / `accepted` / `rejected`）
- コンテキスト
- 決定
- 影響

### 任意セクション

- 代替案（却下した主要案の短い理由）
- 備考（補足や例外）
- 参考資料（関連 ADR、外部仕様）

#### セクション順序

- 影響 → 代替案 → 備考 → 参考資料（ → 付録）

### ADR 間参照（リンク）の運用

- 本文中は参照名（例: `ADR-0002`）だけを書く
- 相互参照のリンクは `参考資料` セクションに相対リンクとして集約する

### 設計ログ (Design log)

- `docs/design-log/` に ADR と同名のファイルを作成できる
- 参考資料にリンクを置く
- ADR 本文には議論の全文や思考過程を書かない

例:

- `docs/design-log/0000-adr-document-format.md`

### 実装詳細の扱い

- ADR 本文には実装詳細（コード断片、SQL/DDL 等）を原則として書かない
- 必要な場合は `参考資料` の後に付録を置いてよい
- 独立した文書として必要に応じて整理もするが決定時点の差分が重要なら付録で固定化する

### 言語・書式

- 日本語を第一として作成する（）
- Markdown を基調とし、インライン装飾は最小にする

### 既存 ADR の扱い

- ステータスが `accepted` または `rejected` になった ADR の本文・付随するデザインログは原則として書き換えない
- 方針変更が必要な場合は、新しい ADR を起票し、置き換え関係は `参考資料` に記す

## 影響

- 重要決定の記録方法が統一され、後から「なぜそうしたか」を追える
- 決定の背景や却下案が最小限で記録され、再検討コストが下がる
- ADR 本文の可読性と運用性が保たれる
