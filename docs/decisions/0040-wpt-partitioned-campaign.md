# ADR-0040: WPT の分割 campaign 実行と累積レポート

## ステータス

accepted

## コンテキスト

ADR-0038 では、固定した対象範囲全体の実行だけが継続的な WPT 進捗レポートを更新し、個別 test の実行結果は更新に使用しないと決定した。

現在の対象範囲は 1,200 を超える test URL を含む。
一つの wptrunner process で全 URL を順次実行すると、未実装機能に起因する timeout が積み重なり、実行が完了するまで進捗を確認できない。
中断した実行の完了済み結果も次の実行へ引き継げないため、対象範囲の拡大に対して全件実行をレポート更新条件とする運用が成立しない。

一方、任意の個別調査結果を単純に足し合わせると、異なる WPT revision、対象範囲、palim build、または実行条件の結果が混在する。
長時間の分割実行から現在の到達点を確認するには、同じ条件で開始した実行集合を識別し、途中結果を安全に累積できる単位が必要である。

## 決定

- 固定した対象範囲全体を分割して測定する単位を WPT campaign とする
- campaign は WPT revision、include と exclude、palim build、および WPT runner の実行条件を固定する
- campaign 開始時に対象 URL を manifest から列挙し、一つの test URL を一つの独立した実行単位として処理する
- 実行単位は複数 worker へ配布し、既定の同時実行数を 10 とする
- 各実行結果は上書きせず、campaign に属する attempt として個別に保存する
- campaign の集計処理だけが、互換性を確認した attempt を test URL 単位で累積する
- 同じ URL を再実行した場合は、campaign が割り当てた順序で最後に完了した有効な attempt を採用する
- 結果が存在しない対象 URL は ADR-0038 と同じく `pending` として扱う
- worker 自体の停止や結果 file の欠落は test result に読み替えず、未完了の実行単位として再実行可能にする
- 一つの worker が実行枠を占有し続けないよう、test 自体の timeout とは別に実行単位全体の終了期限を設ける
- 集計は一定の完了件数または一定時間ごと、および campaign の停止時と完了時に行う
- 累積レポートには campaign の識別情報、状態、集計時点、および実行済み数を記録する
- campaign が進行中または中断済みでも累積レポートを更新できるものとし、未完了分は `pending` として明示する
- report file の更新は集計処理が原子的に行い、worker は report file を直接変更しない
- campaign は中断後に同じ条件から再開でき、既に有効な結果がある URL は既定では再実行しない
- campaign に属さない個別 test の調査結果は、引き続き継続的な進捗レポートへ反映しない
- 固定条件のいずれかが変わった場合は新しい campaign とし、異なる campaign の結果を自動的に混在させない

この決定は、ADR-0038 の「対象範囲全体の一回の実行だけが継続的な進捗レポートを更新する」という制約を置き換える。
進捗の母数、URL と subtest の集計単位、および `pending` の意味は ADR-0038 の決定を維持する。

## 影響

- timeout を含む test URL を複数 worker で分離して処理でき、遅い test が後続 URL 全体を止めにくくなる
- campaign の完了を待たずに、同じ固定条件で得られた現在の実行済み数、成功数、および失敗分類を確認できる
- 中断後に未完了 URL から再開でき、完了済み URL の再実行を避けられる
- 一回の全件実行ではなく、固定した対象集合を分割して得た結果集合が継続的な計測結果になる
- report が途中状態を表す場合があるため、campaign の状態と `pending` 件数をレポート利用者が確認する必要がある
- worker の実行、attempt の保存、queue の回復、互換性検査、および原子的な集計を管理する処理が必要になる
- 複数 worker 分の CPU、memory、および container 実行環境を同時に使用する
- 既存の一時実行結果は campaign の固定条件を証明する metadata を持たないため、自動取り込みの対象にできない

## 代替案

### 一つの wptrunner process で全対象を実行し続ける

途中結果の再利用と中断後の再開ができず、timeout が多い対象範囲ではレポート更新までの時間が長すぎるため採用しない。

### wptrunner の process 数だけを増やす

一つの実行内で並列化はできるが、実行単位ごとの永続化、途中集計、および中断後の未完了 URL からの再開を満たさないため採用しない。

### 過去の個別実行結果を directory 全体から無条件に集める

異なる source、対象範囲、および実行条件を判別できない結果が混在し、現在の到達点として解釈できなくなるため採用しない。

### 機能領域ごとに大きな shard を固定する

実装は単純になるが、timeout が集中する shard が実行枠を長時間占有し、完了済み結果の回復単位も粗くなるため採用しない。
